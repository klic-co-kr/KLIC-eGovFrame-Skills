# KLIC Effort Router

작업의 규모·위험도를 티어로 판정하고, 단계별(계획/검토/구현/리뷰/검증) 모델·에포트를 정해진 서브에이전트로 배정하는 조직 스킬이다. 판정을 출력한 뒤 작업을 수행한다.

```text
Decision(티어 판정) → Requirement → Acceptance → Task → Evidence → Learning
```

> Claude Code 전용 — 라우팅은 서브에이전트 시스템(~/.claude/agents/, effort frontmatter)에 의존.
> Codex CLI·Gemini CLI에서는 티어 판정과 Output Contract만 유효하다.

## When to Use

- 작업 착수 전 규모·위험도 판정이 필요할 때
- 계획·구현·리뷰를 서브에이전트에 위임할 때
- 단계 사이 인계 형식·진행 상태 운반이 필요할 때 (계획→구현→리뷰)
- 모델·에포트 배정 근거가 필요할 때
- 보안 감사·출시 검토를 준비할 때

## 프로젝트 티어 ≠ 작업 티어

klic-spec-intake의 MVP/Core/Product/RFP는 **프로젝트 티어**(스펙 범위), 본 스킬의 S/M/L/XL은 **작업 티어**(실행 자원)다. 같은 프로젝트 안에서도 작업마다 작업 티어를 다시 판정한다.

## 1. 티어 판정

- **S**: 단순 버그 수정, 텍스트/스타일, 단일 파일 변경 (테스트 로직 변경 없음)
- **M**: 기능 추가, 리팩터링, 분기 로직 수정, 영향 2~5파일
- **L**: 대형 모듈, 아키텍처 변경, 고위험 핵심 모듈, 5파일 초과
- **XL**: 코어 엔진 구현, 전체 시스템 리팩터링 (코어 엔진 프로토타입 포함)
- **보안감사**: 보안 감사·출시 검토 트랙

**폴백**: 서로 다른 티어 지표가 충돌할 때(파일 수는 S, 위험 지표는 L 등) 상위 티어를 택한다. 자원 과투자 비용 < 결함 유출 비용.

**은닉 변수 — 해당하면 한 티어 올린다:**

- **요청 경로 동작 변경**: 모든 요청이 지나는 경로(필터·인터셉터·인증·라우팅)의 *동작 자체*를 바꾸는 변경. 경로 위의 국소 로직 추가는 해당 안 함
- **보안 통제 자체**가 변경 대상
- **코드만으로 판별 불가한 변수**(배포 토폴로지·프록시 경계): 해당하면 상향과 함께 확인 질문 1개를 사용자에게 먼저 던진다

**긴급 트랙**: 운영 장애 핫픽스는 티어 판정 후 ③구현을 선행하고 ②검토·④리뷰를 사후 일괄 수행한다. 장애 복구를 검토 대기시키지 않는다.

## 2. 라우팅 테이블 (에이전트 화이트리스트)

아래 테이블의 에이전트만 호출한다. `~/.claude/agents/`에 테이블 밖 파일이 있어도 무시한다 — **존재 ≠ 허가**.

### S
- ① 계획: 생략
- ② 검토: 셀프
- ③ 구현: 메인 세션 직접 / 위임 시 `klic-coder-medium` (haiku)
- ④ 리뷰: `klic-review-pr-high` (텍스트·스타일만 변경 시 생략)

### M
- ① 계획: `klic-plan-high`
- ② 검토: 생략 (plan-high 재호출 금지 — 자기 산출물 검토는 검토가 아니다)
- ③ 구현: `klic-implement-med`
- ④ 리뷰: `klic-review-pr-high`

### L
- ① 계획: `klic-plan-high` (Phase 분해 필수)
- ② 검토: `klic-plan-adversary-xhigh` 팬아웃 ●●● (기본 3렌즈)
- ③ 구현: `klic-implement-med` (Phase당 ≤5파일, 격리 필요 시 worktree)
- ④ 리뷰: `klic-review-pr-xhigh` → 최종 판정 권위는 klic-pr-review-gate

### XL
- ① 계획: `klic-plan-xhigh`
- ② 검토: `klic-plan-adversary-xhigh` 팬아웃 ●●● (5렌즈)
- ③ 구현: `klic-implement-xhigh` / 직렬 임계경로 코어만 `klic-core-xhigh` (기준: klic-plan-xhigh 산출물의 임계경로 식별)
- ④ 리뷰: `klic-review-pr-xhigh` → 최종 판정 권위는 klic-pr-review-gate

### 보안감사
- `klic-security-audit` + 교차 검증 1건 이상 (리뷰 에이전트 1명 또는 상위 세션 재판정). CRITICAL 즉시 최상단 보고.

## ●●● 팬아웃

`klic-plan-adversary-xhigh`를 병렬 스폰, 프롬프트마다 렌즈 1개:

- **기본 3렌즈** (L티어): 완전성 / 기술적 오류 / 위험
- **5렌즈** (XL티어): + 단순성 / 검증성

**반려 게이트 (라운드 상한 2회):**

- CRITICAL은 단독 거부권이 아니다 — 다른 렌즈 1개 이상이 동일 결함을 독립 확인하거나, 상위 세션이 확인한 뒤에만 반려
- 라운드 2회 도달 시 무한 재검토 대신 사용자 에스컬레이션 (수정안 목록 + 누적 비용 동반 보고)
- 병합 산출물 정형: 렌즈 × 심각도 × 발견수 표 + CRITICAL 근거 원문

**심각도 정의** (모든 리뷰 에이전트 공통):

- **CRITICAL**: 데이터 손실, 보안 침투 경로, 롤백 불가 변경, 서비스 전면 장애
- **HIGH**: 기능 오류, 계약 위반, 특정 시나리오 장애
- **MEDIUM**: 품질 저하, 유지보수성 악화
- **LOW**: 정리 사항

## 3. 실행 메커니즘 (제약)

- **effort는 에이전트 파일 frontmatter에 고정** — 호출 시 변경 불가. 다른 조합은 파일 추가.
- **effort의 실발효는 환경 의존이며 조용히 강등될 수 있다** — 검증됨: 카탈로그 미수록 모델(GLM 프록시)에서 xhigh는 high로 자동 강등 (스폰된 에이전트 내 `CLAUDE_EFFORT` 프로브로 확인). 강등되면 xhigh와 high 계획의 차이는 프롬프트 내용뿐이다. 라우팅의 본질은 effort 수치가 아니라 **역할·산출물 분리**다. Output Contract의 effort는 설정값이며 실발효 값과 다를 수 있음을 전제한다.
- **model은 호출 시 덮어쓰기 가능** — `Agent(model: 슬롯명)`. 슬롯(sonnet/opus/haiku/fable)의 실체는 환경별 프록시 매핑을 따른다.
- **호출 허가는 화이트리스트** — 테이블 밖 에이전트명(tdd-guide, code-reviewer 등)은 설치 여부와 무관하게 호출 금지.
- **증거기반 보고** — 구현 에이전트 완료 보고는 테스트 '결과 서술'이 아니라 실행 명령 원문 + exit code. 상위 세션은 핵심 테스트 1회 재실행을 기본 절차로.
- **메인 세션 effort는 `/effort`(대화형)로만 변경** — S티어 상향은 사용자 안내로 처리. '막힘' = 동일 접근 2회 연속 실패 또는 테스트 재적화.
- 에이전트 파일은 본 스킬 디렉터리 `agents/`에 동봉. 스킬 갱신 시 `agents/*.md` 재복사 필수 (README 업데이트 절차 참조).

## 4. klic-pr-review-gate와의 관계

④ 리뷰 에이전트는 검토를 수행하고 발견사항을 출력한다. merge 여부의 **최종 판정 권위는 klic-pr-review-gate**가 가진다. 리뷰 에이전트 판정과 게이트 판정이 갈리면 게이트가 우선한다.

## 5. 상태·인계 계약 (M티어 이상 — S티어·긴급 트랙 ③선행 구간 제외)

역할 배정은 티어 판정이 하고, **무엇이 다음 단계로 살아남는지는 이 계약이 정한다**. 서브에이전트 호출은 각각 무상태다.

적용 제외 2개: **S티어**(계획 생략·셀프 검토 — §3의 증거기반 보고만 적용), **긴급 트랙의 ③구현 선행 구간**(장애 복구를 롤백·검토로 대기시키지 않는다 — §1).

### 단계 인계 = 증거번들 (주장-근거 레코드)

| 단계 | 역할(HoH¹) | 산출 계약 |
|------|-----------|-----------|
| ①계획 | Project Planner | 수정 대상(우선순위) + 보존 제약 + **검증 요구(claims)** — 산출물 미수정 |
| ③구현 | Developer | 변경 파일 + 실행 증거(명령 원문·exit code) |
| ④리뷰 | QA Tester | (주장, 근거, 판정) 레코드 — 판정만, 수정 없음² |

- ①계획의 **검증 요구**는 계획 번들 파일에 남고, **④리뷰 프롬프트에 전문 주입**된다. 리뷰는 claims 검증과 **claims 밖 신규 결함의 별도 보고**를 둘 다 수행한다.
- **보존 제약**("이미 동작하는 X는 깨뜨리지 않는다")은 ③구현 프롬프트에 그대로 복사된다. 깨뜨리면 ④리뷰 gap — 자가 점검이 아니라 계획-리뷰 대조로 잡힌다.
- ②검토(계획 적대 검증)는 HoH에 없는 층이다 — 라우터가 더 엄격한 쪽. 그대로 유지한다.

### 단계 상태 = state.json (메인 세션 단일 writer)

서브에이전트는 state.json을 쓰지 않는다 — 완료 보고만 하고 **메인 세션이 1회 패치**한다. 팬아웃 병렬 보고는 메인이 병합해 한 번에 반영한다. 위치 = **과업 루트 `<task-id>/state.json`** (worktree 격리 시에도 본체 경로 고정 — 체크아웃 안에 두지 않는다).

```json
{"task": "<task-id>", "tier": "L",
 "phase": "plan|adversary|implement|review|verify|done|escalated",
 "round": {"adversary": 0, "review": 0},
 "claims": [{"claim": "...", "status": "pending|gap|verified", "evidence": "..."}],
 "bundle": "<계획 번들 경로>", "next": "adversary"}
```

- **패치 규칙**: 단계 완료 = 1회 패치. 기존 키 유지(merge, not replace), **키 삭제는 값 `null`**. gap 해결 = status 전환(gap→verified), 레코드 삭제 아님. 롤백으로 폐기된 후보의 gap은 status를 `verified`로 전환하거나 evidence에 "superseded(<사유>)"를 남긴다 — stale gap이 다음 검사 목록에 재등장하지 않게.
- **패치 검증**: 열거값·필수 키를 체크하고 위반 시 즉시 재작성한다 — 오염된 상태는 신뢰하지 않는다.
- **재개 규칙**: 컨텍스트 압축·세션 재시작 후 대화 히스토리에서 진행도를 유추하지 않는다. `state.json`의 `next`와 `bundle`로 재개. 소실 시 산출물로 재구성하되 `round`는 직전 보고 기록으로 복원하고 근거가 없으면 1로 두고 **사용자에게 고지**한다.
- **예산**: `round`는 ②반려와 ④regression 재시작을 **각각** 카운트하고 상한은 각 2회(반려 게이트 규칙 그대로 — 범용 예산 아님). 소진 = `phase: escalated` + 수정안 목록·누적 비용 동반 사용자 에스컬레이션.

### 계보 = 롤백 지점 (조건부)

④리뷰 CRITICAL·HIGH regression 판정 시 순서: (a) **상위 세션이 핵심 테스트 1회 재실행으로 확인**한다(②의 교차확인 원칙과 동일 — 리뷰 에이전트 단독 판정으로 롤백하지 않는다). (b) 확인되면 **앵커가 있을 때만** 물러난다 — 앵커 = 구현 착수 전 커밋 또는 worktree 스냅샷. **앵커가 없으면(미커밋 트리) 롤백하지 않고 fix-forward**로 재구현한다 — 무관한 미커밋 변경을 파괴하지 않고, 사용자의 커밋 정책을 대신하지 않는다. rollback 후 `next: implement`. 앵커로 돌아가도 gap이 남으면 계획 결함이므로 ①로 회귀해 번들을 갱신한다.

¹ Harness-of-Harness (Shanghai AI Lab, 2026) — 계획자/개발자/QA 3역할·증거번들·계보. ² 읽기전용은 리뷰 에이전트 정의의 도구 제한으로 강제(Edit/Write 미부여).

## Output Contract

작업 시작 전 항상 아래 형식으로 출력한다.

```text
[Effort Router]
- 판정 티어: {S | M | L | XL | 보안감사}
- 작업 단계: {계획 | 검토 | 구현 | PR 리뷰 | 검증}   # state.json phase 대응: 계획=plan, 검토=adversary, 구현=implement, PR 리뷰=review, 검증=verify
- 적용 에이전트·모델·에포트: {agent-file} ({model} / {effort})
- 팬아웃: {OFF | ON: klic-plan-adversary-xhigh × 3 (완전성/기술적오류/위험)}
- 단계 상태: {phase → next} (§5 적용 시 state.json 기준)
- 실행 지침 요약: {해당 티어 제약조건 인용}
```

실제 Agent 호출의 subagent_type·model 파라미터는 Contract에 명시한 값과 일치해야 한다. 불일치 = 라우팅 위반.

## 자주 하는 실패

| 실패 | 현실 |
|------|------|
| 테이블 밖 에이전트명 지목 (tdd-guide, code-reviewer 등) | 유령 에이전트 — 화이트리스트만 호출 |
| 존재하는 파일 = 호출 가능으로 해석 | 존재 ≠ 허가. 테이블 밖 파일은 무시 |
| 자의적 모델 배정 ("sonnet이 적당해 보임") | 배정은 티어 매트릭스가 결정, 재량 아님 |
| Contract만 출력하고 테이블 무시 | Contract의 에이전트명 = 실제 호출 subagent_type과 일치 필수 |
| CRITICAL 단독으로 무한 재검토 | 라운드 상한 2회, 초과 시 사용자 에스컬레이션 |
| 파일 수만 보고 판정 | 은닉 변수(요청 경로 동작 변경·보안 통제·토폴로지) 확인 먼저 |
| 단계 산출을 산문 인수인계로 전달 | 다음 단계가 재구성에 실패한다 — 인계는 증거번들(주장-근거 레코드) 계약 |
| ④리뷰를 검증 요구 주입 없이 진행 | 리뷰가 자의적 기준이 된다 — ①계획의 검증 요구 전문을 ④리뷰 프롬프트에 주입 |
